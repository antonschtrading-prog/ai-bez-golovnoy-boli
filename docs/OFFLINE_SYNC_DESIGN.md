# Подготовка офлайн-синхронизации (этап 2)

Дата: 10 ноября 2026. Технический модуль: `progress-outbox.js`.

## Что готово

- Очередь исходящих изменений (outbox), **без фоновой сети**, без автоматической синхронизации текущих учебных страниц.
- Изоляция по **непрозрачному серверному идентификатору аккаунта**: отдельный ключ `ai-course-outbox-v1:<accountId>`.
- Отдельный полный снимок разделов; проверка схемы через `CourseSyncModel`.
- Стабильный идентификатор операции для повторной отправки: серверный API поддерживает идемпотентность.
- Переотправка того же снимка при сетевом сбое, без удаления из очереди.
- При `409 revision_conflict` кандидат остаётся в очереди, отправка блокируется до **явного решения пользователя**.
- Перед удалением подтверждённой операции проверяются ожидаемая ревизия и точное совпадение возвращённых сервером разделов.
- Повреждённый или чрезмерно большой outbox не перезаписывается автоматически.

## Работа клиента (пока только API модуля)

1. Только после подтверждённого входа пользователь выбирает/создаёт аккаунт.
2. Отдельная операция сохраняет заготовленный полный снимок с последней известной серверной ревизией: `enqueue(sections, baseRevision)`.
3. При явном действии пользователя `flush(client)` вызывает подготовленный `CourseProgressClient.save`.
4. Если сеть недоступна, возвращается статус `retry`. Снимок и ID остаются.
5. Если сервер отвечает конфликтом, возвращается `conflict`. **Автоматический last-write-wins запрещён**.
6. Успешный проверенный ответ убирает операцию из очереди.
7. `discard()` — явная отмена локальной операции, не вызывается автоматически.

## Важные границы безопасности

- Токены не сохраняются в outbox; только payload учебного прогресса и технические метаданные. Тем не менее, тексты работ в локальном браузере **не зашифрованы**.
- API доступа пока не подключён к формам курса. Нельзя незаметно привязать существующий анонимный прогресс к аккаунту.
- Пока сохраняется **одна** ожидающая полная версия на аккаунт. Повторное добавление блокируется, чтобы избежать потери уже подготовленного черновика. Для живого автосохранения нужен отдельный outbox по стабильным ID работ и транзакционное хранилище (IndexedDB).
- `localStorage` не обеспечивает атомарность при конкурентных вкладках. Для полной защиты потребуются Web Locks или транзакции IndexedDB.
- В полной серверной синхронизации необходимы отдельные процессы входа, выхода, очистки аккаунтного состояния и подтверждения переноса данных.
- Серверный ответ не признаётся успешным, если ревизия/снимок не совпали. При сохранении ответа от сервера, но отказе локального хранилища отправка повторяется с тем же ID и должна быть идемпотентной.
- В API перед отправкой **необходимо** получить серверную ревизию и согласовать все разделы, так как PUT заменяет их целиком. Автоматического перехода от `localStorage` к облачному обновлению пока нет.

## Проверка

`tests/outbox.test.cjs`: запись в очередь без сети, повтор после сбоя, защита несинхронизированного черновика, конфликты, разделение аккаунтов, повреждённые и неверные данные, явное удаление. На этапе подготовки также выполнены имитационные вызовы модулей с несколькими сценариями.

Следующий безопасный этап: `IndexedDB`-слой и тесты двух вкладок; затем интерфейс **явной** привязки прогресса к аккаунту, вход/выход, outbox отдельных учебных записей.

## Планировщик согласования перед PUT

`progress-sync-planner.js` использует существующую `CourseMergeRules.audit` в режиме без побочных эффектов:
- `prepare(localSections, {revision,sections})` проверяет обе копии, сохраняет серверные разделы, которых нет в локальной копии, и объединяет только безопасные независимые записи;
- при разных значениях одного черновика или экзамена возвращает `status: conflicts`, причём `proposed: null` — никакой кандидат не отправляется;
- `queueIfSafe(outbox,plan)` явно добавляет проверенную копию в outbox с известной ревизией;
- если сервер успел изменить данные после чтения, окончательным арбитром остаётся `If-Match` API, который вернёт 409.

Тесты в `tests/sync-planner.test.cjs` проверяют сочетание независимых уроков, конфликт черновиков, сохранение серверных разделов и отклонение неверных ревизий/схем.

**Ограничение:** сравнение пока консервативное; UI для разрешения конфликтов и реальная авторизация ещё не готовы. Пользователь должен отдельно подтвердить перенос анонимного прогресса в конкретный аккаунт.

## Транзакционный IndexedDB (третья подготовительная часть)

`progress-indexeddb.js` предоставляет `CourseIndexedStore.open({dbName})` и операции `get(accountId,section)`, `update(accountId,section,expectedRevision,value)`. Обновление проходит через единую транзакцию `readwrite`, которая выполняет проверку ревизии и запись атомарно внутри объекта `progress`. При несоответствии ревизии возвращает конфликт, а не перезаписывает данные.

Записи разделены ключом `accountId:section`, идентификаторы ограничены безопасным набором символов. Перед записью применяется проверка структуры данных из `CourseSyncModel`. На `versionchange` соединение закрывается, чтобы другие вкладки могли обновить схему.

В браузерный Chromium-сценарий добавлены одновременные попытки записи от двух соединений: ровно одна из двух записей должна пройти; вторая должна получить конфликт. Проверяется отсутствие данных другого аккаунта, устаревшая ревизия и некорректный формат. Пока существующий курс продолжает работать через локальные ключи: переключать всё на IndexedDB до полной миграции и тестов Safari **нельзя**.

**Не считается выполненным:** тест действительно двух независимых вкладок Safari, полный перенос сохранений в IndexedDB, синхронизация IndexedDB/outbox с живым сервером, удаление/отзыв локальных данных при выходе из аккаунта.
