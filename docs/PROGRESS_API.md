# Прогресс, восстановление и будущая синхронизация

## Риски и обратимость

1. История: старые ключи и формат разделов сохраняются. Перед заменой записываются прежний и новый снимки; отказ записи истории останавливает замену. Никаких сетевых отправок. До 20 снимков на раздел, до 2 млн символов на снимок. После успешного сохранения старые снимки сверх лимита удаляются. При частом вводе это история последних сохранений, не долговременный архив и не каждая версия за всё время. При заполнении квоты браузера требуется экспорт; текущий текст нужно скопировать до закрытия.
2. Восстановление: заменяет **весь раздел**, не только текст одного задания; показывает полный JSON до подтверждения. Текущее состояние сначала сохраняется. Если раздел изменён после предпросмотра, запись отклоняется, кандидат сохраняется в истории.
3. Миграция: только дополнительный ключ `ai-course-migration-v2`, содержит исходную копию и конверт v2. Существующие разделы не переписываются. Повтор той же миграции идемпотентен; другой источник не вытесняет старую миграцию. Неизвестные версии, разделы и небезопасные вложенные поля отклоняются.
4. Сервер: SQLite-транзакция объединяет изменение прогресса, историю и квитанцию операции. Ошибка любой записи откатывает всё. Изменений производственной базы в этой сессии нет.

## Совместимость

Поддерживаются `ai-course-progress-snapshot-v1`, `ai-course-full-local-backup-v1` (журнал оставляется в исходной копии, но исключается из учебных разделов v2), `ai-course-sync-envelope-v2`, отдельный экспорт лаборатории `ai-course-study-lab-v1`, основной курс `{type:"ai-course-progress",schemaVersion:3|4|5,state}`. Сохраняются неизвестные безопасные поля внутри известных разделов. Исторические файлы учеников недоступны: тесты на синтетических примерах и формате экспорта текущего кода.

Полный прежний экспорт через маршрут по-прежнему содержит текущий прогресс и журнал, **не историю снимков**. История скачивается отдельно на странице восстановления. Скачанная история — архив для диагностики; импорт истории через интерфейс пока не реализован. При восстановлении старого полного экспорта версии исходных разделов сохраняются. Многоключевой импорт по-прежнему имеет best-effort rollback: localStorage не обеспечивает транзакции при аварийном закрытии процесса.

## Ограничение локальной конкуренции

Каждая вкладка запоминает исходное значение. При обнаруженном изменении другой вкладкой новый черновик сохраняется как `conflict`, основной ключ не заменяется. Дополнительная проверка выполняется непосредственно перед записью. Это не атомарный compare-and-swap: узкая гонка между проверкой и записью остаётся, поскольку API localStorage синхронный и не транзакционный. Оба кандидата сохраняются независимыми UUID-снимками. Для гарантированного согласования всех вкладок следующий этап — асинхронный IndexedDB/Web Locks и переработка обработчиков сохранения. Перед ручным восстановлением закрывать остальные вкладки. Серверная конкуренция уже защищена транзакцией.

## HTTP API v1

У всех методов обязательный `Authorization: Bearer <session>`. Токен не принимается из URL или body. Идентификатор аккаунта извлекается только из серверной сессии. SQL параметризован; токены хранятся SHA-256-хешами с истечением срока. Нет паролей и самодельной регистрации. До публикации выбрать готового провайдера OIDC/email, добавить серверный обмен подтверждённой идентичности на сессию, выход/отзыв и ограничения запросов. Провайдер в этой сессии не подключался.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/progress` | `{revision,sections}`, ETag |
| PUT | `/v1/progress` | `{sections}`, обязательны `If-Match: "N"` и `Idempotency-Key` |
| GET | `/v1/progress/versions` | Последние 50 версий только текущего аккаунта |
| POST | `/v1/telegram/link` | `{initData}`, привязка к уже авторизованному аккаунту |

Успешный PUT повышает серверную ревизию. Повтор той же операции возвращает прежний результат. Повтор ID с другим payload → 409. Хранятся последние 500 квитанций; более старый повтор с прежней ревизией отклоняется по конфликту ревизии. Разная ревизия → 409 с текущей копией. Клиент должен сохранить свой кандидат локально, показать различия и отправить осознанное решение с **новым** ID и актуальной ревизией. Автоматического last-write-wins нет. PUT заменяет полный набор разделов; частичную копию нельзя отправлять без предварительного чтения и согласования.

401 — нет действующей сессии; 403 — origin вне списка; 415 — не JSON; 428 — нет ревизии; 422 — неверная структура; 413 — тело больше 1 МиБ; 500 — ошибка хранилища без раскрытия внутренних деталей. `Cache-Control: no-store`, `nosniff`, точный CORS allowlist, без cookies. Клиентский адаптер `progress-client.js` требует HTTPS (кроме loopback), не хранит токены, запрещает redirect и не делает запросов до явного вызова. Он ещё не подключён к автосохранению страниц.

## Telegram Mini App

Открывает тот же интерфейс и проходит вход в тот же аккаунт, затем опционально привязывает Telegram. Не создаём второй профиль по имени/аватарке и не объединяем аккаунты автоматически. Сервер проверяет HMAC-SHA256 `initData`, уникальность полей, `auth_date` (5 минут, допуск будущего времени 30 секунд), положительный числовой ID. Одно initData нельзя повторно использовать для привязки. Связь 1:1; перепривязка запрещена. Бот-токен — только в `TELEGRAM_BOT_TOKEN` серверного окружения. При отсутствии токена метод возвращает 503. Вход через Telegram, выпуск сессии и UI привязки ещё не реализованы. SDK не загружается и бот не создаётся.

Официальный алгоритм: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app
SQLite Node.js: https://nodejs.org/download/release/v24.0.0/docs/api/sqlite.html

## До публичного запуска

- Реальный провайдер авторизации, отзыв/ротация сессий, rate limits, пользовательские квоты, тест истечения сессии и смены аккаунта.
- Раздельные локальные хранилища по аккаунтам; явное согласие на перенос анонимного прогресса, outbox и повтор при потере сети. Сейчас глобальные localStorage-ключи анонимны, поэтому API нельзя незаметно подключить к ним.
- HTTPS reverse proxy, защищённая серверная папка SQLite, отдельный системный пользователь, резервирование SQLite через backup API, проверенный restore и мониторинг диска. Базу/WAL нельзя обслуживать статическим сервером. В production нужны лимиты хранения квитанций и текстов по байтам.
- Политика сроков хранения, удаление аккаунта и всех копий. Локальная история и экспорты содержат открытые тексты; не защищены от другого человека в том же профиле браузера или XSS.
- Реальные Safari/iPhone и Telegram WebView, отказ сети, полное закрытие браузера, реальные архивные копии. GitHub Pages исполняет только статический интерфейс, не этот API.

Секреты, `.env`, SQLite и результаты тестов исключены из git. Ни один production-secret не использован. Все токены в автотестах синтетические.
